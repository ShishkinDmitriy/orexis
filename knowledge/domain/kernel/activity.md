# What it is

An [event](/domain/kernel/event.md) has no duration; an activity has nothing else. It begins when a
[policy](/domain/kernel/policy.md) decides that the events it heard call for it, runs for as long as
the work takes, and ends. PROV's word is the one meant: an activity is a `prov:Activity`, of a class
its package declares beneath it - `planning:Planning`, a pass of the Planner, and `execution:Walking`,
`execution:Adopting`, `execution:Superseding` and `execution:Resolving` - each started by a trigger of its own.

Its start and its end are instants, and PROV's own: a `prov:Start` and a `prov:End`, each an event
said as the activity starts and ends, reached from it by `prov:qualifiedStart` and `prov:qualifiedEnd`
and stamped `prov:atTime`. A start names its triggers as PROV does, by `prov:entity`: not the event
heard but the thing it was about - the belief graph that changed, the plan written, the step whose
landing fell due. So no event triggers an event, and the one that brought a trigger is reached through
that entity, whose generation it was. A start or an end may be what another package's policy hears. An
event said while the activity runs - a want derived, a search ended, a step taken - names it, as PROV's
generations and usages name theirs by `prov:activity`. Several triggers may start one activity: two
readings revised in one pass start one planning.

An activity may hold others. Planning a pass holds one search per scope, each started and ended
inside it, and once the scopes run apart the searches overlap in time while the planning that started
them has ended.

# Where it runs is a separate question

What an activity is says nothing of the thread it runs on. One that writes the store runs on the
mind, as a job; one that waits on the outside - a fetch, the model's call, a timer - is a task; one
that computes for seconds without the store, a scope's search, runs off both. Its start and its end
are said the same way wherever it ran.

# Who reads it

Nobody reads an activity's start or its end out of the journal: a planning begins and a walk every second, and kept
for good as two events they would be most of it. `orexis-journal/` hears them on the watch and keeps each activity,
as it ends, as ONE entry of the [journal](/domain/kernel/journal.md), named by the activity and kept for the
journal's window: its class, when it started and ended on the agent's clock, how long it took in real seconds
(`orexis:tookS`, the agent's clock standing still while it computes), what started it (`prov:wasStartedBy`, each
entity its start names), the activity it was begun inside (`dcterms:isPartOf`), and what it generated
(`prov:wasGeneratedBy`): each event said while it was open, with the class the event said it is and the instant it was said at
(`prov:generatedAtTime`), and each graph
its turn wrote, which the kernel says of the activity the turn ended last.

So what caused what is a query over the journal and no package is asked: an activity started by something another
generated was caused by it, `?b prov:wasStartedBy ?x . ?x prov:wasGeneratedBy ?a`, and a cycle through four
packages is a path. Two links are not yet there: what sensing takes in is written outside any activity, and a
command that starts an actuating is generated by none.

What ships them is the other half of the pair, `orexis-journal-otlp/`: a task that wakes on a timer,
reads the activities the journal holds that it has not sent, and POSTs them to a tracer as spans - an activity a
span, one begun inside another its child and a trace the outermost with everything inside it, an event said in it
an event on the span at its own instant, and what caused it a LINK to the span of the activity that generated what
started it. A link says which event that was, by its class and its name, and the mark on the causing span carries
the same name, so which event of one activity began another is read in the tracer. An
activity is marked `orexis:shippedTo` the tracer only once it accepted the POST, so one that is away is told later
what it missed, for as long as the journal's window holds it. It hears nothing and no package imports it
([packages-meet-by-events-policies-and-activities](/decisions/packages-meet-by-events-policies-and-activities.md)).
